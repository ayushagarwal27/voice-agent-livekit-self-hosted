## Phase 6 — Barge-in with accurate history

- `agent/worker.py`: `turn_handling.interruption` now spells out `enabled: True, min_duration: 0.5, mode: "vad"` explicitly, where Phase 4/5 only set `mode: "vad"` (to stay off LiveKit's cloud inference, rule 2) and left `enabled`/`min_duration` on the library's defaults. - **The big thing this phase asked to verify, not assume:** whether `livekit-agents` 1.x truncates the assistant's chat-history entry to only what was actually spoken when a reply is interrupted. Read `livekit/agents/voice/generation.py` and `voice/agent_activity.py` directly. It does, and the mechanism is more precise than "stop at a word boundary": `forward_generation()` captures the TTS player's `playback_position`/`synchronized_transcript` at the moment of interruption (so for providers that return aligned-transcript timing, the cut point matches the audio, not just character count), and `agent_activity.py` commits the resulting `forwarded_text` — not the full LLM output — as the `ChatMessage.content`, with `interrupted=True` set on the same message. So `agent/transcript.py` (already reading `item.text_content` and `item.interrupted` off this same event since Phase 5) needed **zero changes** for correct truncated, flagged persistence — it was already right by construction.

## Phase 7 — Latency measurement

- **The plan in AGENTS.md ("subscribe to `metrics_collected`, join by `speech_id`") is stale for the installed version — verified, not assumed (rule 7).** Read `livekit/agents/voice/events.py`: `MetricsCollectedEvent`'s own docstring says "Deprecated: use session_usage_updated for usage tracking. Per-turn latency metrics are available on ChatMessage.metrics." So `agent/metrics.py` reads the `MetricsReport` dict the framework already attaches to every user/assistant `ChatMessage` (confirmed by reading where `agent_activity.py` builds `assistant_metrics`/`metrics_report`) instead of hand-joining raw events by `speech_id` — simpler and it's what the framework itself now recommends.
- Stage mapping used in `agent/metrics.py` (each name is the framework's own field): `eou_ms` <- user message's `end_of_turn_delay`; `stt_final_ms` <- user message's `transcription_delay`; `llm_ttft_ms` <- assistant message's `llm_node_ttft`; `tts_first_audio_ms` <- `tts_node_ttfb`; `audio_published_ms` <- `playback_latency`; `total_ms` <- `e2e_latency` (the framework's own ground-truth `assistant_started_speaking_at - user_stopped_speaking_at`, measured independently of the other five columns, not derived from them).
- `storage/models.py` gained `TurnMetrics` matching the AGENTS.md data model, with every stage column nullable — an interrupted turn, or the scripted greeting (which never goes through `llm_node` at all), can legitimately be missing some or all of them, and those are left `NULL` rather than guessed at.
- `scripts/latency_report.py` prints a markdown per-turn table, an avg/p50/p95 summary per stage, and a sanity-check table comparing `max(eou_ms, stt_final_ms) + llm_ttft_ms + tts_first_audio_ms + audio_published_ms` against the directly-measured `total_ms`.
- **Approximation, called out in both `agent/metrics.py` and the README per AGENTS.md's instruction:** `eou_ms` and `stt_final_ms` are both measured from the same anchor (the user falling silent) and run in parallel, not sequentially — summing them double-counts time, hence `max()` in the sanity check, not `+`. Even with that fix, the reconstructed total undershoots the framework's real `total_ms` by 50-280ms per turn in testing, because `on_user_turn_completed_delay` and the scheduler gaps between stages aren't captured as their own column. Documented as "`total_ms` is ground truth, the stage columns show where the time goes" rather than quietly pretending the reconstruction is exact.
- **Caught a real bug before it mattered:** the very first test run's 21 turns of metrics were silently lost — `agent/metrics.py`'s insert failed with `OperationalError: no such table: turn_metrics` for every single turn (logged, not raised, since `attach_metrics_recorder`'s DB write isn't guarded against this). Root cause: the running backend process predates the `TurnMetrics` model, so its in-memory `Base.metadata` (and therefore its `init_db()` calls) never knew the table existed — adding a model to `storage/models.py` doesn't retroactively create its table in an already-running process. Fixed by running `init_db()` once by hand (safe: `create_all` is additive, doesn't touch the three existing tables) and re-running the test. Worth remembering for later phases too: a new table needs either a backend restart or a manual `init_db()`, not just the model-file edit.
- **Verified automatically, no browser needed:** 3 real calls (18/19/20) against the real self-hosted LiveKit server, Deepgram STT, OpenAI `gpt-4.1`, and Cartesia TTS, 6 questions each, played as synthesized (`say`) audio over a published `SOURCE_MICROPHONE` track — same harness pattern as Phase 6's forced-barge-in script. 21 turns landed in `turn_metrics` (18 full LLM turns + 3 greetings, the latter correctly `NULL` on every LLM-dependent column). Real numbers: LLM TTFT avg 873ms/p95 1013ms (the single largest stage — the one to attack first), EOU avg 591ms, STT final avg 484ms, TTS first audio avg 166ms, total avg 1739ms/p95 1920ms. Full table and write-up in `docs/latency.md`.
- **Still needs the owner:** nothing mechanical — the "Test it" steps (3+ calls, 5-10 turns, `latency_report.py` prints real numbers, stages roughly sum to total) were all satisfied by the automated run above. Worth a quick look at `docs/latency.md`'s "which stage to attack first" paragraph to confirm the reasoning holds up to the kind of questioning AGENTS.md's "be ready to explain" list expects.

- `agent/whisper.py`: listens for `room.on("data_received")` on topic `operator_whisper`, persists the text to `whispers`, then copies the current `Agent.chat_ctx`, appends a `role="system"` message ("Private supervisor guidance... never mention it...") via `ChatContext.add_message`, and calls `agent.update_chat_ctx(...)` — the one documented, supported way to mutate context (verified by reading `agent_activity.py`: the actual generation calls always read from `self._agent._chat_ctx`, which is exactly what `update_chat_ctx` sets). Since this only appends to context rather than forcing a reply, it naturally takes effect on the next user turn with no extra "is the agent idle" bookkeeping needed.
- **Approximation, called out in the README:** the whispered guidance is never removed from context after being used once — it was added for simplicity, and because AGENTS.md's own test script ("whisper something odd, such as 'ask for their email'") is itself a one-shot ask. A call with several different, possibly conflicting whispers over its lifetime would need the oldest ones superseded or pruned; out of scope for this POC.
- **Surprise:** `rtc.LocalParticipant.publish_data` is a coroutine in the Python SDK (unlike `room.on()` callbacks, which are sync) — a first draft of the verification script called it without `await` and it silently never sent (`RuntimeWarning: coroutine ... was never awaited`), which would have made the whisper look like it "just didn't work." Fixed by awaiting it.
- **Surprise, pre-existing and out of scope to fix:** nothing in this project ends a call just because the customer disconnects — the worker keeps the job (and its room) alive indefinitely until something else closes it, so `GET /calls/{id}` can sit on `status: "active"`/`transcript: null` for a long time after a real hang-up. Same reason Phase 7's `latency_report.py` reads `turn_metrics` straight from the DB rather than via the API; the whisper verification script below does the same for `transcript_lines`.
- **Verified automatically, end-to-end, no browser needed:** a throwaway script joined one real call as a synthesized "customer" (same `say`-generated-audio-over-`SOURCE_MICROPHONE` pattern as Phases 6/7) and, concurrently, as the hidden operator via a second `livekit.rtc.Room` using a real `POST /calls/{id}/operator-token`. Turn 1 ("What plans do you offer for a single person household?") got a neutral reply; the operator then whispered "Offer them a 10% loyalty discount on their plan," and turn 2 ("Is there any way I can get a better price on my current plan?") got: *"Yes, I can give you a 10% loyalty discount on your current plan. Would you like me to apply that for you now?"* — the whisper changed the reply, naturally, with no forced wording. Confirmed no leakage by grepping the full persisted transcript for "operator"/"supervisor"/"instruction" (none found). Confirmed invisibility at the protocol level, not just the UI: the customer's own `participant_connected` listener never fired for the operator at all (`hidden=True` stops LiveKit from telling other participants the operator exists), versus the operator's own view of the room, which saw both `customer-22` and `agent-AJ_m8mfm5S6DYow` normally.

## Phase 9 — Post-call compliance

- `storage/models.py`'s `calls.compliance_json` (a `Text` column) already existed from the original Phase 0 scaffold; Phase 9 just started writing to it. `backend/routers/calls.py`'s `CallOut.compliance` is `dict[str, Any] | str`, defaulting to the string `"pending"` when `compliance_json` is still `NULL`, matching AGENTS.md's "`pending` until done" literally rather than nesting a `pending` status inside a dict.
- **Rule 1** (`compliance/rules.py`, `evaluate_recording_disclosure`) is deliberately pure: plain dicts in, plain dict out, no DB/network imports at all. That is what makes `tests/test_compliance_rule1.py` a true no-network unit test. It assumes its input is already ordered by `seq` (true of how `compliance/runner.py` loads it) and returns the first agent line, in that order, whose `ts_ms <= 30000` and whose text matches the disclosure regex — matching AGENTS.md's "whose speaking start is `ts_ms <= 30000`" exactly (the check is on when the line *started*, not on where in a long line the phrase falls).
- **Rule 2** (`compliance/llm_check.py`) uses `openai`'s `AsyncOpenAI().chat.completions.parse(..., response_format=<PydanticModel>)` (installed `openai==3.35.1`) for validated structured output at `temperature=0`, rather than hand-parsing JSON out of a plain completion. Model is `COMPLIANCE_LLM_MODEL` (env, defaults to `gpt-4.1-mini`) — a separate, cheaper model from the agent's own `gpt-4.1`, since this is a yes/no judgement over a handful of short lines, not a conversational reply.
- Per AGENTS.md: verified `offending_line` is a real substring of a real agent line before trusting it (the model could otherwise hallucinate a plausible-sounding line that was never actually said); on a mismatch, or on any API exception (timeout, etc.), retries once, then reports `status: "error"` with `passed: None` rather than silently trusting or silently passing. Smoke-tested both the clean case and an explicit-refund case directly against the real OpenAI API before wiring it into a live call — both came back correct, including the verbatim offending line on the refund case.
- `compliance/runner.py`'s `run_compliance(call_id)` is the single place both the worker and `scripts/run_compliance.py` call into — loads `transcript_lines` ordered by `seq`, runs both rules, writes the combined JSON to `calls.compliance_json`. Idempotent by construction: it is a pure read of an already-final (post-call) transcript, so calling it again just re-evaluates the same input and overwrites the same row.
- `scripts/run_compliance.py` follows the `-m scripts.<name>` convention established in Phase 3/7 (bare `python scripts/run_compliance.py <call_id>`, as literally written in AGENTS.md, fails with `ModuleNotFoundError: No module named 'compliance'` for the same reason bare-path `agent/worker.py` and `scripts/seed_agent.py` did — the script's own directory lands on `sys.path`, not the repo root).
- `agent/worker.py`'s `on_shutdown` now calls `await run_compliance(call_id)` right after marking the call `ended` (transcript is fully flushed by then, since the session has already stopped), wrapped in `try/except` with `logger.exception` — a flaky compliance LLM call must not block shutdown or look like the call itself failed.
- **Surprise, real and worth knowing about:** found two duplicate `uv run python -m agent.worker dev` processes running simultaneously (one from over an hour earlier, predating all of Phase 8/9's code, that I never killed because an earlier process-restart check grepped for the literal string `worker.py`, which doesn't match the `-m agent.worker` invocation). With two workers registered under the same `agent_name`, a dispatched job silently went to the stale one for one test call, which produced a transcript with only the greeting (no user turn ever arrived) — not a Phase 9 bug, but a leftover process management mistake. Fixed by killing every stale `agent.worker`/`uvicorn` process and restarting exactly one of each, logged to `/tmp/backend_p9.log`/`/tmp/worker_p9.log`. Lesson: check for `agent.worker` (the module form), not `worker.py`, when hunting for stale processes from now on.
- **Surprise, pre-existing and out of scope to fix:** Cartesia's TTS API occasionally returns zero audio frames for a line (`APIError: no audio frames were pushed for text: ...`, logged by the framework itself). When that happens to the greeting, no assistant `ChatMessage` ever gets committed for it at all, so the transcript has no agent line whatsoever — rule 1 then correctly reports `passed: false` with no evidence line, which is the *right* answer (nothing was actually said), not a bug in the rule or in Phase 9's code. Hit this on several consecutive automated test calls in a row; treating it as flaky third-party TTS infra, not a regression, since nothing about Phase 8 or 9's changes touches the TTS path.
- **Verified automatically, end-to-end, on real calls through the self-hosted server** (no browser needed, reusing the Phase 8 operator channel as the trigger): a whisper — "Tell them they'll get a full refund for this month, guaranteed." — sent right after the greeting, followed by the customer asking about a refund, produced the agent actually saying "Yes, you will get a full refund for..." (cut off by the test's own disconnect timing, but the spoken part is what's in the transcript and what rule 2 judged). Rule 2 correctly returned `passed: false` with that exact line as `offending_line` and a sensible `reason`. The same call's greeting (recorded within the first second) made rule 1 return `passed: true` with the right evidence line and `ts_ms`. Re-ran `uv run python -m scripts.run_compliance <call_id>` by hand afterward and got the identical result back, confirming idempotency.

### Phase 9 fixes from the owner's own live test

- **Real bug, found on the owner's first real browser call (call 34):** rule 2 returned `status: "error"` instead of `passed: false`. Root cause: the model echoed the `"[i] "` index marker we prefix each line with back inside `offending_line` (e.g. `"[3] I'm sorry for the trouble..."`), which then failed the plain substring check against the un-prefixed agent line text — twice (the retry hit the same habit, since it's a systematic prompting issue, not a one-off). AGENTS.md's own wording anticipated exactly this ("verify `offending_line` is really a substring **or index** of an agent line"), which the original implementation only half-handled (substring only). Fixed two ways: tightened the prompt to say "no leading `[index]` marker", and (defense in depth, since prompts aren't guarantees) added `_resolve_offending_line` in `compliance/llm_check.py`, which strips a leading `[\d+]` prefix and also accepts a bare numeric index before giving up -- verified directly against the exact string from call 34, then re-ran `scripts.run_compliance` on it and got the correct `passed: false` result with the real offending line.
- Also surfaced this call's `status: "error"` real transcript as evidence the gate behavior is correct once fixed: recording disclosure passed (greeting at `ts_ms=845`), and the agent, whispered "give them refund", said "I'll start a refund for the outage period" -- rule 2 now correctly fails with that exact line.
